## 1. 项目概述

### 1.1 一句话描述

**让嵌入式固件开发从"人工逐行审查"进化到"AI 自主闭环验证"。**

### 1.2 要解决的问题

嵌入式固件开发存在一个被长期忽视的结构性矛盾：

```
软件侧：AI 让代码生成速度提升 100 倍
硬件侧：烧录、测试、调试速度一点没变

结果：AI 生成的代码越多 → 硬件瓶颈越突出 → 开发效率反而下降
```

传统工具（Keil、IAR、PC-lint、Saleae）全部是**"发现问题"**的工具，没有一个能**"自动修复"**。嵌入式工程师 60% 的时间花在 debug 上，而这 60% 中的大部分问题是**已知规则的违规**（delay 阻塞、引脚冲突、ISR 臃肿、动态内存），理论上完全可以自动化。

### 1.3 解决方案

**三层守卫引擎 + AI 闭环修复**：
- **约束引擎**：编码规范自动扫描 → 违规自动修复（delay/malloc/乘除/ISR 行数）
- **契约引擎**：引脚分配、时钟树、DMA 映射、中断优先级的冲突自动检测
- **Golden Trace 引擎**：逻辑分析仪波形自动采集 → 黄金数据对比 → 差异分析

### 1.4 愿景

```
Phase 1 (约束引擎)         → 让 AI 遵守嵌入式编码规范
Phase 2 (契约引擎)         → 让 AI 避免硬件设计错误
Phase 3 (Golden Trace)     → 让 AI 验证硬件行为正确性
Phase 4 (规格即代码)       → 让 AI 从芯片手册推导实现
Phase 5 (数字孪生)         → 在仿真中完成 90% 的开发验证
```

### 1.5 核心指标

| 指标 | 当前行业水平 | 目标（Phase 3 达成） |
|------|------------|-------------------|
| 编码规范违规率 | 人工审查，遗漏率 ~30% | 自动扫描 + 自动修复，遗漏率 <1% |
| 引脚冲突发现时机 | 烧录后调试阶段 | 编码阶段自动拦截 |
| 逻辑 bug 在硬件上发现比例 | ~70% | <20%（Mock 测试 + 仿真拦截） |
| 每次变更平均烧录次数 | 5-10 次 | 1-2 次 |
| 驱动回归测试 | 几乎不做 | Golden Trace 自动化 |

## 2. 市场分析

### 2.1 市场空间

```
全球嵌入式开发者：约 400-600 万（2024）
  ├── MCU 裸机开发：约 160-240 万（最痛，工具最烂）
  ├── RTOS 开发：   约 140-210 万
  └── Embedded Linux：约 100-150 万

第一阶段目标市场：国产 MCU 原厂（约 30 家）
  每家 SDK 团队 + FAE 团队：10-50 人
  每家年工具支出预算：10-100 万
  可触达 TAM：30 × 50 万 = 1500 万/年（中国市场）

第二阶段扩展市场：方案公司 + ODM
  中国方案公司估计：500-1000 家
  每家年工具支出：1-5 万
  可触达 TAM：500 × 2 万 = 1000 万/年
```

### 2.2 客户画像

| 客户类型 | 痛点强度 | 决策周期 | 付费意愿 | 获取难度 |
|---------|---------|---------|---------|---------|
| **国产 MCU 原厂** | ★★★★★ | 3-6 个月 | 30-80 万/年 | 中（需要关系） |
| **方案公司/ODM** | ★★★★ | 1-2 个月 | 2-5 万/年 | 低（开源漏斗） |
| **硬件创业团队** | ★★★★ | 2-4 周 | 5000-2 万/年 | 低（社区口碑） |
| **个人开发者** | ★★★ | 即时 | 99 元/月 | 低（免费版转化） |

### 2.3 为什么是 MCU 原厂

```
原厂的 SDK 开发是巨大的成本中心，但直接影响芯片销量：

  华大 CIU32F003 案例：
  ├── SDK 团队：10 人
  ├── FAE 团队：20 人  
  ├── 客户因 SDK bug 放弃选型的比例：估计 15-25%
  └── SDK 质量每提升 10% → 芯片销量提升 3-5%

  如果 EmbedAI Guard 能提升 SDK 质量 50%，减少 FAE 工时 40%：
  → 单家年价值 200-500 万
  → 付费 50-100 万 ROI 极高
```

### 2.4 市场时机

- **国产替代潮**：30+ 家国产 MCU 原厂，每家都在抢客户，SDK 质量是核心竞争力
- **AI Copilot 普及**：嵌入式开发者已习惯 AI 辅助编码，但发现 AI 不懂嵌入式约束
- **RISC-V 兴起**：新架构的 SDK 从零开始，有机会从一开始就建立质量标准
- **竞品真空**：Copilot/Cursor 专注于通用编程，嵌入式是明确空白

### 4.3 约束规则 DSL 设计

```yaml
# rules/embedded/no_delay.yml
id: "EMBED-001"
name: "禁止阻塞延时"
severity: error
category: "禁止阻塞延时"
description: "禁止使用 HAL_Delay() 等阻塞延时函数，改用定时器驱动"
patterns:
  - "HAL_Delay("
  - "delay_ms("
  - "delay_us("
  - "vTaskDelayUntil(?!.*portMAX_DELAY)"  # 仅允许有限延时
fix_strategy:
  type: "suggest"
  template: |
    /* 改为定时器驱动：
    static uint32_t tick = 0;
    if (HAL_GetTick() - tick >= {delay_ms}) {{ ... }}
    */
auto_fix: false  # 需要人工确认
chip_specific: false
```

```yaml
# rules/embedded/no_divide.yml  
id: "EMBED-003"
name: "禁止除号"
severity: warning
category: "禁止乘除"
description: "使用移位操作替代乘除法"
patterns:
  - type: "ast_node"
    kind: "binary_expression"
    operator: "/"
fix_strategy:
  type: "auto"
  conditions:
    - divisor_is_power_of_two:
        transform: "value / {d} → value >> {log2(d)}"
    - divisor_is_constant:
        transform: "value / {d} → (value * {inverse}) >> {shift}"
    - otherwise:
        action: "warn_only"
auto_fix: true
chip_specific: false
```

### 7.2 为什么不是 Copilot/Cursor

```
Copilot 在嵌入式上的盲区：
├── 不理解芯片约束：不知道 PA9 不能同时做 UART_TX 和 GPIO
├── 不理解时序约束：不知道 QSPI CLK 不能超过 80MHz
├── 不理解编码规范：会生成 HAL_Delay()，不提示违规
├── 不理解中断约束：ISR 中生成复杂处理逻辑
└── 不理解硬件调试：看不到波形，没有回归能力

EmbedAI Guard 的定位：
  不是替代 Copilot，是在 Copilot 的输出上加一层嵌入式专用质量门禁。
  类比：Copilot = 写草稿的人，Guard = 审核草稿的资深嵌入式工程师。
```
